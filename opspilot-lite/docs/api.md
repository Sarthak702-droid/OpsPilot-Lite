# API

All `/api/*` routes require a Clerk bearer token. Onboarding routes are `GET /api/organization/me` and `POST /api/organization` (name, industry, currency, timezone). Membership is resolved from the verified Clerk subject and database, never a browser supplied organization ID.

Read routes: `/api/dashboard`, `/api/products`, `/api/inventory`, `/api/customers`, `/api/invoices`, `/api/suppliers`, `/api/signals`, `/api/actions`, `/api/recommendations`, `/api/ai/health`.

Business routes: `GET /api/sales` and `GET /api/sales/:id`; `POST /api/sales` and `PATCH /api/sales/:id` save drafts with `customer_id`, `sale_date`, `tax`, `discount`, and `items` (`product_id`, `quantity`, `unit_price`, `discount`). `POST /api/sales/:id/complete` commits stock and sale movements once. `GET /api/purchase-orders` and `GET /api/purchase-orders/:id`; `POST /api/purchase-orders` and `PATCH /api/purchase-orders/:id` save drafts with supplier, number, dates, and item quantity and unit cost. `POST /api/purchase-orders/:id/request-send` creates an approval action. After a different manager approves it, `POST /api/actions/:id/execute` sends the PO through SMTP. `POST /api/purchase-orders/:id/receipts` records `item_id`, `quantity`, and a unique `reference` for a partial or full delivery. `POST /api/purchase-orders/:id/cancel` cancels an unsent draft. Owners and admins use `POST /api/purchase-orders/:id/resolve-send` with `outcome: SENT | NOT_SENT` after investigating an uncertain delivery.

Payments: `GET /api/payments`, `POST /api/payments` with `invoice_id`, decimal `amount`, `payment_date`, `payment_method`, and unique `reference_number`; `POST /api/payments/:id/reverse` with a reason restores the invoice balance and retains the payment record. Business writes require OWNER, ADMIN, or MANAGER.

Workspace routes: `GET /api/organization/settings`; OWNER or ADMIN can `PATCH /api/organization/settings` with `overstock_days` (30–365) and `high_value_threshold` (positive decimal). `GET /api/organization/users` lists members. OWNER or ADMIN can `POST /api/organization/invitations` with email and role, receiving a one-time token, or `PATCH /api/organization/users/:id/role`. A signed-in user without a membership can `POST /api/organization/invitations/accept` with that token.

Mutations: `POST /api/import` multipart CSV/XLSX (`type`, `file`, optional JSON `mapping`); `POST /api/import/preview` returns headers and sample rows; `POST /api/import/pdf/preview` accepts a PDF and returns extracted text and optional MiMo field suggestions; `POST /api/import/pdf/commit` accepts the PDF plus JSON `review`, then stores it in R2 and writes the reviewed record and audit event. PDF commits require configured R2. Other mutations: `POST /api/ai/ask` (`question`), `POST /api/ai/stream` (SSE), `POST /api/actions/:id/approve`, `/reject`, `/execute`. Imports and action decisions require OWNER, ADMIN, or MANAGER. Errors use `{ "error": { "code", "message", "request_id" } }`. `/health` is process liveness; `/ready` requires PostgreSQL and Redis but not MiMo. `/metrics` exposes aggregate HTTP request counts and durations in Prometheus format.
